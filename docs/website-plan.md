# Website plan: the first presentable version, live on its own domain

Written 2026-09-08 after John reversed the earlier deferral of a standalone site (definitions.md, "Where it lives publicly"). This is the plan for putting the first version of The Belt Equation on a dedicated website, built alongside the roadmap rather than after it, and fitting with the two active projects it sits beside: TimeAssembler, which holds the project's story, and Sentient Horizons, which publishes the essay. Steps are numbered 20 onward so they never collide with the roadmap's 1 to 19, and each is tied to the roadmap step it waits on.

Under-promoted still holds. The site exists, family and friends get the link, and wider announcement is a separate decision (roadmap step 16).

## What version one shows

Five pages, and nothing more, are needed before family and friends can be sent the link:

1. **Home.** The question in large type, the equation beneath it, one paragraph on what the project is, the headline number for A2 under each of the four scenarios, and the tree visual.
2. **The tree.** One page per factor listing its nodes, and one page per node showing its name, description, resolution criterion, source, horizon, dependencies, probability by scenario with rationale and date, and status. This is the repo's data, rendered so a reader who will never open a TOML file can argue with a specific node.
3. **How the numbers are computed.** The methodology document (roadmap step 12), rendered, with the scenario table and the Contact Clause beside it.
4. **The story so far.** The changelog, rendered, and the project's recent progress pulled from TimeAssembler at build time. One place to see what has changed and why, without a second place to write.
5. **Disagree with something.** How to name a missing node or move a probability: a link to a GitHub issue template in the public repo, and a note on how critique gets folded into the tree with a changelog line.

The Sentient Horizons essay (roadmap step 14) is not a page here. It lives on Sentient Horizons and links to the site; the site links back. The family-and-friends version (roadmap step 15) becomes the home page's paragraph and the tone of the whole site.

## How it fits together

    data/*.toml  ──┐
    CHANGELOG.md ──┤  scripts/export.py  ──►  site/src/data/*.json  ──►  Astro build  ──►  dist/  ──►  wrangler deploy
    TimeAssembler ─┘        │
    (worklog, via API)      └── scripts/compute.py run  (numbers)  and  dot output  ──►  Graphviz  ──►  site/public/tree.svg

- **Python owns the data.** The export script reads the tree with the same loader the compute script uses, so the site can never show a tree that fails validation. It writes plain JSON files the site reads at build time. Nothing in the browser touches TOML, the API, or a key.
- **Astro owns the pages.** Same generator, folder layout, and deploy pattern as Sentient Horizons and Hearth and Void: `site/` in this repo, `npm run build`, `wrangler deploy` of `dist/` to Cloudflare Workers static assets, custom apex domain attached.
- **TimeAssembler owns the story.** At export time the script fetches the Belt Equation project's worklog entries and roadmap from the TimeAssembler API using the credentials file on the Mac, and writes them into the story page's JSON. The key stays on the Mac because the build runs on the Mac.
- **The tree visual is a committed picture.** The compute script gains a `dot` command that writes the dependency graph in Graphviz's text format, colored by factor; Graphviz on the Mac renders it to an SVG that is committed under `site/public/`. Static, as roadmap step 13 allows.

## Decisions, with confidence and alternatives

Per the ground rule of 2026-09-08. DECIDED 2026-09-08: proposed by Claude with confidence and alternatives, all nine accepted by John. The domain name remains his to choose at step 20.

1. **Astro 5 static site in `site/` of this repo.** High confidence: it is what Sentient Horizons and Hearth and Void use, so one set of tools, one mental model, and shared page components and styles. Alternative: plain HTML generated by Python, which fits the standard-library ethos of the scripts and needs no JavaScript toolchain, at the cost of rebuilding navigation, styling, and Markdown rendering that Astro gives for free and of looking nothing like the sister sites. Second alternative: a separate repo for the site, which keeps this repo pure data and documents but means two repos to keep in step on every tree change.
2. **Cloudflare Workers static assets, deployed with wrangler after a local build.** High confidence, by precedent. Alternative: Cloudflare's git-connected build, which rebuilds on every push, at the cost of needing Python, Graphviz, and the TimeAssembler key in Cloudflare's build environment. The local build keeps all three on the Mac. Revisit if John wants the quarterly scan to publish itself from a push.
3. **A Python export script feeds the site JSON.** High confidence: validation and the numbers already live in Python, and the site should never duplicate that logic. Alternative: Astro reading the TOML files directly through a plugin, which is fewer steps but means two readers that can disagree.
4. **The tree visual is a Graphviz-rendered SVG committed to the repo.** Moderate confidence. It is simple, deterministic, and enough for version one. Alternative: a client-side layout in JavaScript with hover and click through to node pages, which is a better reading experience for a fifty-node graph and the natural version two once the tree has stopped moving. Cost now: a week of front-end work before there are numbers to show.
5. **The story page pulls from TimeAssembler at build time with the local key.** Moderate confidence. It gives one place to write and keeps the site honest about progress. Alternative: a hand-written updates page, which drifts. Second alternative worth noting for TimeAssembler's own roadmap: a public read-only endpoint for one project's worklog, which would let any site show a project's story without a key; not needed for version one.
6. **A dedicated apex domain, John's choice of name.** Moderate confidence on the form, none on the name. Alternative: a subdomain of sentient-horizons.com, which costs nothing and reinforces the family of projects, at the cost of the project reading as a blog post rather than a thing of its own. John asked for a dedicated site, so a dedicated domain follows.
7. **Visual cohesion by copying Sentient Horizons' base styles and typography into this site.** Moderate confidence. Alternative: a shared design package installed by all three Astro sites, which is the correct engineering answer and more machinery than three sites kept by one person need. Copy now, extract later if a fourth site appears.
8. **Critique through GitHub issues with a template.** High confidence: the repo is public, issues are durable and quotable, and folding one into the tree is a commit that can cite it. Alternative: comments on the site itself, which needs a service and moderation.
9. **No analytics in version one.** Moderate confidence. Sentient Horizons has an analytics proxy that could be copied; under-promoted means the numbers would say little for months. Add it if and when John decides to post beyond family and friends.

## Steps, alongside the roadmap

Each step names the roadmap step it waits on. Targets follow the roadmap's phase dates.

20. **Scaffold the site and pick the domain** (waits on nothing; target 2026-09-21). Create `site/` with Astro 5, copy the wrangler configuration pattern and base styles from Sentient Horizons, build a home page holding the question and the equation with placeholder numbers, and deploy it to the workers.dev preview address. John chooses and registers the domain; it is attached at step 25, not now. Done when the preview address serves the home page.
21. **The export script and the node pages** (waits on roadmap step 8, the review pass; target 2026-10-12). Write `scripts/export.py` to produce the site's JSON from the tree and the changelog. Build the factor pages and node pages from it. Done when every node in `data/` has a page on the preview site and the validator and the export agree on the count.
22. **The tree visual** (waits on roadmap step 7, the dependency edges; target 2026-10-19). Add a `dot` command to the compute script, render the SVG with Graphviz, commit it, and put it on the home page. Done when the picture on the site matches the tree in the repo.
23. **The numbers and the methodology page** (waits on roadmap steps 10 and 12; target 2026-10-26). Export the `run` results into JSON, show the scenario table on the home page and the node pages, and render the methodology document. Done when the home page's headline numbers are the compute script's output and nothing else.
24. **The story page and the critique page** (waits on nothing after step 21; target 2026-11-09). Fetch the project's worklog and roadmap from TimeAssembler in the export script, render the story page with the changelog, write the GitHub issue template, and write the disagree page. Done when a change in TimeAssembler shows on the preview site after one export and build.
25. **Go live** (waits on roadmap step 15, the family-and-friends version, and step 16 for anything beyond that; target 2026-11-16). Attach the domain, publish, send the link to family and friends. Done when the domain serves the site and the first outside person has read it.
26. **One-command publish** (waits on step 25; ongoing). A single script that runs export, compute, Graphviz, the Astro build, and wrangler deploy, so the quarterly scan (roadmap step 17) ends with the site updated. Done when a quarterly scan is published with one command.

## Deferred, and why

- **Interactive tree** (hover, click through, filter by factor): version two, once the tree has stopped changing shape.
- **A public TimeAssembler endpoint for a project's story:** belongs on TimeAssembler's roadmap, not this one.
- **Analytics, comments, a newsletter:** only if the posture changes at roadmap step 16.
- **Automatic rebuild on push:** only if the quarterly scan turns out to be a chore to publish by hand.
